## 一、调研背景

### 1.1 为什么调研字幕

Phase 0 的核心交互链路是：**播放视频→暂停→选中字幕→右键→AI 结合课件+逐字稿答疑→多轮追问**。这条链路的每一步都依赖字幕文件——没有字幕，选中无从谈起，时间窗截取也无从谈起。

但调研中发现一个真实痛点：**用户手上可能只有视频，没有字幕文件**。这引出了"自动生成字幕"的需求，进而需要调研字幕的来源、格式、生成工具。

### 1.2 调研发现的关键误解

在需求澄清阶段，曾出现一个误解："字幕文件只有时间戳，文本是另外的文稿"。本调研澄清了这个误解：**字幕文件（SRT/VTT）同时包含时间戳和文本，是配对出现的**。基于此，Phase 0 做出了"字幕=逐字稿"的架构决策（见第七章），简化了数据模型。

### 1.3 调研覆盖的问题

- 字幕从哪里来？（四种来源）
- 字幕文件长什么样？（格式详解）
- 字幕文件和纯文稿有什么区别？（关键对比）
- 没有字幕怎么办？（自动生成工具对比）
- Phase 0 选什么方案？（Whisper 本地生成）
- 字幕和逐字稿是不是两个文件？（字幕=逐字稿决策）
- 时间窗截取怎么利用字幕？（技术方案）
- 非标字幕怎么处理？（格式检测与容错）
- 字幕怎么在播放器里显示和选中？（ArtPlayer 渲染决策）

## 二、字幕的四种来源

视频字幕按产生方式分为四类，质量和数据形态各不相同。

### 2.1 硬字幕（烧录/内嵌）

**定义**：字幕文字直接"印"在视频画面里，和视频是一体的。

**特点**：
- 没有独立的字幕文件，文字是画面像素的一部分
- 播放器无法控制字幕的显示/隐藏/样式
- 无法选中字幕文本（文字是图像不是文本）
- 无法提取时间戳

**提取方式**：只有 OCR（光学字符识别）能提取，效果差、错误率高

**Phase 0 立场**：**不支持**。硬字幕无法选中、无法提取时间戳，核心交互链路无法实现。

**常见场景**：早期影视资源、部分 B 站搬运视频、电影盗版

### 2.2 软字幕（外挂/独立文件）

**定义**：字幕是一个独立文件（.srt / .vtt / .ass），播放器加载后叠加显示在画面上。

**特点**：
- 有独立文件，文字是文本不是图像
- 播放器可控制显示/隐藏/样式/位置
- 可以选中字幕文本（取决于播放器渲染方式）
- 每条字幕都有精确时间戳（开始时间 + 结束时间）
- 质量最高——通常由 UP 主用 Aegisub、Arctime、剪映等工具人工校对

**制作工具**：Aegisub（专业字幕编辑）、Arctime（跨平台字幕制作）、剪映（自动识别+人工校对）

**Phase 0 立场**：**这是 Phase 0 的目标字幕类型**。核心交互链路完全依赖软字幕。

### 2.3 平台自动生成字幕

**定义**：视频上传到平台（B 站、YouTube）后，平台用 AI 语音识别自动生成字幕。

**特点**：
- 也是带时间戳的（识别时按时间分段）
- 质量取决于语音清晰度和平台识别能力，通常中高
- 可从平台下载为 SRT/VTT 格式
- B 站 CC 字幕的底层数据是 JSON 格式（`{body:[{from, to, content}]}`），下载工具可转 SRT
- 部分平台自动生成字幕带样式标签（`<c>` `<i>` `<b>`），需清洗

**Phase 0 立场**：**支持下载后的 SRT/VTT，但拒绝原始 JSON 格式**。B 站 CC JSON 需用下载工具导出为 SRT/VTT 后再放入 materials 目录。

### 2.4 工具生成字幕

**定义**：用户用语音识别工具（Whisper、剪映、讯飞等）对视频文件自动生成带时间戳的字幕文件。

**特点**：
- 输入是视频文件，输出是 SRT/VTT/ASS
- 质量取决于工具水平和语音清晰度
- 可本地部署（Whisper）或云端调用（阿里云、讯飞）
- 是"用户只有视频没有字幕"场景的解决方案

**Phase 0 立场**：**选用 Whisper 本地生成**（详见第五、六章）。

### 2.5 四种来源对比

| 来源 | 有无独立文件 | 时间戳 | 可选中 | 质量 | Phase 0 支持 |
|---|---|---|---|---|---|
| 硬字幕 | ❌ 无 | ❌ 无 | ❌ 不可 | — | ❌ 不支持 |
| 软字幕 | ✅ 有 | ✅ 有 | ✅ 可（自定义渲染层） | 最高（人工校对） | ✅ 目标类型 |
| 平台自动生成 | ✅ 有（可下载） | ✅ 有 | ✅ 可 | 中高 | ⚠️ 需转 SRT/VTT |
| 工具生成 | ✅ 有 | ✅ 有 | ✅ 可 | 中高（Whisper 高） | ✅ Whisper 本地生成 |

## 三、字幕文件格式详解

### 3.1 SRT（SubRip）格式

**最通用的字幕格式**，几乎所有播放器都支持。

**格式规范**：
- 每条字幕由 4 行组成：序号、时间戳、文本、空行
- 时间戳格式：`HH:MM:SS,mmm --> HH:MM:SS,mmm`（**逗号**分隔毫秒）
- 文本可以是多行

**示例**：
```
1
00:00:15,000 --> 00:00:18,000
这就是一条字幕文本

2
00:00:18,500 --> 00:00:21,000
这是第二条字幕文本
可以跨多行
```

**Phase 0 处理**：入库时自动转换为 VTT 存储（原 SRT 保留不删除）。

### 3.2 VTT（WebVTT）格式

**W3C 标准格式**，Web 播放器（含 ArtPlayer）原生支持。

**格式规范**：
- 首行必须是 `WEBVTT`
- 时间戳格式：`HH:MM:SS.mmm --> HH:MM:SS.mmm`（**点号**分隔毫秒，与 SRT 的逗号不同）
- 无序号行
- 支持样式标签：`<c>`（class）、`<i>`（斜体）、`<b>`（粗体）、`<u>`（下划线）
- 支持 NOTE 注释块、STYLE 样式块、REGION 区域块

**示例**：
```
WEBVTT

00:00:15.000 --> 00:00:18.000
这就是一条字幕文本

00:00:18.500 --> 00:00:21.000
这是第二条字幕文本
可以跨多行
```

**带样式标签的示例**（Phase 0 需清洗）：
```
WEBVTT

00:00:15.000 --> 00:00:18.000
<c.keyword>重要概念</c>：这是一个<i>斜体</i>示例
```

**Phase 0 处理**：
- 标准 VTT（无样式标签）：直接使用
- 带样式标签的 VTT：入库时清洗掉 `<c>` `<i>` `<b>` `<u>` 标签，只保留纯文本

### 3.3 SRT 与 VTT 的差异

| 维度 | SRT | VTT |
|---|---|---|
| 首行 | 无要求（直接是序号1） | 必须是 `WEBVTT` |
| 时间戳毫秒分隔符 | 逗号 `,` | 点号 `.` |
| 序号行 | 有（1, 2, 3...） | 无 |
| 样式标签 | 不支持 | 支持 `<c>` `<i>` `<b>` `<u>` |
| Web 播放器原生支持 | 需转换 | 原生支持 |
| Phase 0 策略 | 入库时转 VTT | 直接使用 |

**转换规则**（SRT → VTT）：
1. 首行加 `WEBVTT`
2. 时间戳中的逗号 `,` 改为点号 `.`
3. 删除序号行
4. 清洗样式标签（如有）

### 3.4 ASS（Advanced SubStation Alpha）格式

**高级字幕格式**，支持复杂样式（字体、颜色、位置、动画、特效）。

**格式规范**：
- 脚本结构：`[Script Info]` + `[V4+ Styles]` + `[Events]` 三个区块
- 事件行格式：`Dialogue: Marked=0,Start,End,Style,Name,MarginL,MarginR,MarginV,Effect,Text`
- 支持覆盖标签（`\N`换行、`\n`软换行、`{\b1}`粗体等）

**Phase 0 立场**：**不支持**。ASS 格式复杂、样式标签与 Web 渲染不兼容、提取纯文本麻烦。检测到 ASS 格式时拒绝扫描，提示用户用字幕工具转换为 SRT。

### 3.5 B 站 CC 字幕 JSON 格式

**B 站自动生成字幕的底层数据格式**。

**格式规范**：
```json
{
  "body": [
    {
      "from": 15.0,
      "to": 18.0,
      "content": "这就是一条字幕文本"
    },
    {
      "from": 18.5,
      "to": 21.0,
      "content": "这是第二条字幕文本"
    }
  ]
}
```

**特点**：
- 时间戳是秒（浮点数），不是 `HH:MM:SS` 格式
- 无序号、无样式标签
- 不是标准字幕格式，播放器不直接支持

**Phase 0 立场**：**不支持原始 JSON**。检测到 JSON 格式时拒绝扫描，提示用户用 B 站字幕下载工具（如"B站字幕下载器"浏览器插件）导出为 SRT/VTT 后再使用。

## 四、字幕文件 vs 纯文稿的区别

这是 Phase 0 需求澄清中发现的关键认知点。

### 4.1 核心区别

| 维度 | 字幕文件（SRT/VTT） | 纯文稿（txt/md） |
|---|---|---|
| **时间戳** | ✅ 每条字幕都有精确时间戳 | ❌ 只有文字，没有时间戳 |
| **可选中** | ✅ 每条字幕是独立文本块，可选中 | ⚠️ 是连续文本，选中没有时间含义 |
| **时间窗截取** | ✅ 按时间戳精准取前后 N 分钟 | ❌ 无法定位到视频时间点 |
| **显示用途** | ✅ 播放器叠加显示在画面上 | ❌ 不能用于显示 |
| **上下文供给** | ✅ 既是显示层，又是 AI 上下文来源 | ⚠️ 只能作为补充上下文，不能定位 |

### 4.2 关键澄清

曾有误解认为"字幕文件只有时间戳，文本是另外的文稿"。**这是错误的**。

字幕文件（SRT/VTT）的每一条都是 **时间戳 + 文本** 的配对：
```
00:00:15,000 --> 00:00:18,000    ← 时间戳
这就是一条字幕文本                ← 文本（和这条时间戳配对）
```

时间戳和文本是**不可分割的配对关系**。正因为如此，Phase 0 做出了"字幕=逐字稿"的架构决策（详见第七章）。

### 4.3 为什么纯文稿不够用

纯文稿只有文字，没有时间戳。如果用户选中了第 15 分 30 秒的字幕提问，系统需要取 12:30~18:30 范围的上下文——纯文稿无法知道哪段文字对应这个时间范围。

只有字幕文件（带时间戳）才能实现时间窗截取。

| 工具 | 类型 | 中文质量 | 成本 | 可集成性 | Phase 0 选型 |
|---|---|---|---|---|---|

### 5.2 为什么选 Whisper

1. **本地部署，零调用成本**：用户已用阿里云百炼的大模型 API（按量付费），字幕生成如果也付费，成本叠加。Whisper 本地生成零调用成本。
2. **Python 生态原生适配**：`pip install openai-whisper`，与 FastAPI 后端无缝集成。
3. **中文识别质量够用**：medium 模型中文识别准确率 >90%，large 更高。
4. **输出标准格式**：直接输出 SRT/VTT，不需要额外转换。
5. **可控可调**：模型大小可选（tiny/base/small/medium/large），可根据机器性能权衡速度和质量。
6. **开源成熟**：OpenAI 开源，社区活跃，文档完善。

### 5.3 为什么不选其他

- **剪映**：桌面 GUI 软件，无编程 API，无法后端集成。适合个人手动生成，不适合自动化。
- **B 站 AI 字幕**：依赖 B 站平台，视频需先上传到 B 站。Phase 0 是独立部署，不应依赖外部平台。
- **阿里云/讯飞**：按量付费，与"本地零成本"目标冲突。且 Whisper 质量已够用，不值得为边际质量提升付费。

## 七、字幕=逐字稿的架构决策（变更6）

### 7.1 问题

架构 v1 设计中提到"字幕"和"逐字稿"两个词，造成混淆：
- 字幕：用于播放器显示
- 逐字稿：完整的授课文本，作为 AI 上下文

这暗示需要两个独立文件——字幕文件用于显示，逐字稿文件用于 AI 上下文供给。

### 7.2 决策：一份文件两用途

**字幕文件就是逐字稿**，不分两个文件。

理由：
- 字幕文件（SRT/VTT）已经包含了完整的授课文本（每条字幕文本拼接起来就是逐字稿）
- 字幕文件还有时间戳，能做时间窗截取
- 如果再单独维护一个纯文稿逐字稿，既冗余又容易和字幕不同步

### 7.3 数据模型简化

**变更前**（架构 v1）：
- materials 表有 `subtitle_path`（字幕文件路径）+ `transcript_path`（逐字稿文件路径）

**变更后**（架构 v2）：
- materials 表只有 `subtitle_path`，删除 `transcript_path`
- `subtitle_path` 既用于播放器显示，又用于时间窗截取取文本

### 7.4 context_builder 实现

时间窗截取直接从 `subtitle_path` 对应的 VTT 文件解析取文本（详见第八章）。

## 八、时间窗截取技术方案

### 8.1 原理

用户选中第 N 条字幕后，系统拿到该字幕的时间戳（如 00:15:30），然后取 **00:12:30 ~ 00:18:30** 范围内（前后各 3 分钟）的所有字幕文本作为 AI 上下文。

**关键特性**：时间窗截取的 token 消耗与课程总长度无关——只取时间窗内的字幕，不管课程是 30 分钟还是 3 小时。

### 8.2 实现（伪代码）

```python
def extract_transcript_window(subtitle_cues, center_time, window_minutes=3):
    """从字幕文件提取时间窗内的文本"""
    start = max(0, center_time - window_minutes * 60)
    end = center_time + window_minutes * 60
    window_cues = [
        cue for cue in subtitle_cues
        if cue["start"] >= start and cue["end"] <= end
    ]
    return "\n".join(cue["text"] for cue in window_cues)

def build_messages(course, selected_subtitle, user_question, history):
    """构造大模型请求的 messages"""
    # 1. 逐字稿时间窗：选中字幕 ±3 分钟
    transcript_window = extract_transcript_window(
        course.subtitle_cues,
        center_time=selected_subtitle["start"],
        window_minutes=3
    )
    # 2. 课件粗筛：按章节取相关部分
    courseware_text = filter_courseware_by_time(
        course.courseware_text,
        course.chapter_timestamps,
        selected_subtitle["start"]
    )
    # 3. 多轮历史：最近 5 轮
    recent_history = history[-10:] if len(history) > 10 else history  # 5轮=10条
    # 4. 拼 messages
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "system", "content": f"课件内容：\n{courseware_text}"},
        {"role": "system", "content": f"逐字稿（当前知识点前后片段）：\n{transcript_window}"},
        *recent_history,
        {"role": "user", "content": f"选中字幕：{selected_subtitle['text']}\n\n我的问题：{user_question}"},
    ]
    return messages
```

### 8.3 与 RAG 的关系

| 维度 | Phase 0 时间窗截取 | Phase 1+ RAG 语义检索 |
|---|---|---|
| 定位方式 | 时间戳硬定位（精准） | 语义相似度（近似） |
| 适用场景 | 字幕（有时间戳） | 课件（无时间戳） |
| token 消耗 | 与课程长度无关 | 与召回数量相关 |
| 工程量 | <1 天 | 3-5 人天 |

**Phase 0 不上 RAG**，因为字幕有时间戳，时间窗截取比语义检索更精准。课件用章节粗筛兜底。Phase 1+ 上 RAG 时，只需替换 `context_builder` 内部的两个函数，调用方无感知。

### 8.4 Token 控制

- 1 小时课程逐字稿全量：5-8 万 tokens（会超 32K 上下文上限）
- 时间窗截取后（±3 分钟）：1.5K-2.5K tokens（与课程长度无关）
- 课件粗筛后：3K-6K tokens
- 多轮历史限 5 轮：5K tokens
- **合计**：1.2 万-1.8 万 tokens，任意长度课程都能塞进 32K 模型

详细 Token 预检阈值见 PRD 第七章：>28K 截断历史到 3 轮 / >30K 截断到 1 轮 / >32K 拒绝请求。

## 九、格式检测与容错（Phase 0）

### 9.1 支持格式

| 格式 | 处理方式 |
|---|---|
| 标准 VTT（无样式标签） | 直接使用 |
| 带样式标签的 VTT（含 `<c>` `<i>` `<b>`） | 入库时清洗标签，只保留纯文本 |
| 标准 SRT | 入库时自动转 VTT 存储（原 SRT 保留） |

### 9.2 拒绝格式

| 格式 | 检测方式 | 拒绝提示 |
|---|---|---|
| ASS/SSA | 首行含 `[Script Info]` 或 `[Events]` | "请用字幕工具（Aegisub/Arctime）转换为 SRT" |
| B 站 CC JSON | 首字符 `{` 且含 `body` 字段 | "请用 B 站字幕下载工具导出 SRT/VTT" |

### 9.3 字幕选中降级链路（L1~L4）

| 级别 | 触发条件 | 行为 |
|---|---|---|
| L1 正常 | 用户选中字幕片段 | 右键 → AI 提问，选中字幕进入提示词框 |
| L2 降级 | 右键时 selection 为空 | 取当前 cue 整条文本，右键 → AI 提问 |
| L3 降级 | 当前无 cue（暂停在无字幕时段） | 只传时间戳，后端用时间窗取逐字稿 |
| L4 兜底 | 字幕层渲染失败 | 输入框旁"插入当前字幕"按钮 + 纯手动输入 |

每级降级 UI 显式提示当前模式。

## 十、ArtPlayer 字幕渲染决策（关联）

> 本章为引用摘要，详细内容见 `architecture.md` 第 1.1.2 节和第 5 章。

### 10.1 不用原生 `<track>` 的理由

ArtPlayer 原生支持 `<track>` 标签加载 VTT 字幕，但**不用原生 track**，因为：

| 浏览器 | 原生 `<track>` 选中行为 |
|---|---|
| Chrome | `::cue` 伪元素，selection 能拿到但范围不准；右键 contextmenu 不触发 cue 元素 |
| Firefox | cue 在独立渲染层，selection 拿不到 |
| Safari | 无法选中 |
| iOS Safari | 完全无法选中 |

字幕选中是 Phase 0 核心交互，原生 track 跨浏览器选中行为不可控。

### 10.2 自定义渲染层

1. ArtPlayer 配置关闭原生字幕显示（`subtitle.show: false`）
2. 自定义绝对定位的 overlay div 作为字幕层
3. 监听 ArtPlayer 的 cue 更新事件，把当前 cue 渲染成 `<div class="subtitle-cue" data-start data-end>文本</div>`
4. 用户用浏览器原生 Selection API 选中（自动支持）
5. 监听 `contextmenu` 拿 `window.getSelection().toString()`，弹右键菜单

详细实现代码见 `architecture.md` 第 5.2 节。

## 附录：调研结论速查

| 决策项 | 结论 |
|---|---|
| Phase 0 字幕来源 | 软字幕（用户自备）+ Whisper 自动生成（无字幕时） |

| 选中降级 | L1~L4 四级降级链路 |
