# Phase 0a 需求评审报告

> 评审角色：需求评审 Subagent（grill-me 方法论 + 轻量商业视角）
> 评审对象：项目提议书 V1.2 + 灵感来源.txt
> 评审边界：Phase 0 范围（核心助学链路 + 管理台配置 + 可换素材）
> 日期：2026-08-23

## 根本性发现

提议书的 Phase 0 = "外部独立演示原型、素材预置、不引入RAG、Token超限属可接受局限、不做文件上传"
本方案 Phase 0 = "可直接拿来用、可换素材、管理台配置大模型、完整播放器体验"
两者不是一回事。提议书所有"原型可接受"风险结论都建立在"演示中短课程样本"前提上，这个前提在 Phase 0 升级后整体失效。

---

## 一、致命遗漏（不解决不能进开发）

### F1. 提议书与 Phase 0 范围根本错位，风险评级需推倒重做
- 提议书 R-05 把"长课程 Token 超限"列为低风险/原型可接受，理由是"原型使用中短课程样本演示"。但 Phase 0 是"用户用真实长课程可直接拿来用"。R-04 把字幕兼容性列为"仅对标准 VTT 开启"——但 Phase 0 是"可换素材"，用户拿非标字幕就直接不能用。
- 整个提议书的风险接受逻辑建立在"演示场景"上。Phase 0 范围扩了，但风险评级没跟着重做。
- 建议：重做风险登记册，把每个"原型可接受"项重新放在"用户真实长课程+自备素材"场景下评级。R-05 至少升到高/中-高。

### F2. 管理台在提议书里完全不存在，从0设计
- 提议书全文 0 次提及"管理台""后台""配置端"。Phase 0 新增的管理台没有任何设计依据。
- 管理台决定大模型 key 存哪、谁能改、怎么不泄露——直接影响后端形态、部署形态、安全模型。
- 建议：补管理台最小设计：访问入口、配置存储位置、鉴权方式、key 保护策略、配置热更新机制、支持的模型协议范围。

### F3. "可换素材"的承载方式未定义，与浏览器沙箱冲突
- 提议书明确写"素材本地预置、不做文件上传"。Phase 0 升级为"可换素材"但没说怎么换。
- H5 前端不能读取本地任意目录（浏览器沙箱）。如果用户换素材靠"放约定目录"，必须有后端读文件——后端职责放大。如果靠"管理台上传"，那需要文件存储+元数据管理。两条路都没定。
- 建议：明确素材接入方式（三选一）：①管理台上传+后端存储；②后端约定目录+管理台扫描；③前端 <input type=file> 运行时加载（不支持持久化）。每种方式的格式约束、大小限制、关联方式都要写清。

### F4. Token 超限不是"可接受局限"，是 Phase 0 核心链路直接断
- 一门 1 小时课程逐字稿 3-5 万字 ≈ 5-8 万 tokens，加课件再加多轮历史，任何 32K 上下文模型都顶不住。Phase 0 用户拿真实课程第一时间就触发。
- 核心链路第一次提问就报错或截断到答非所问，"可直接拿来用"承诺破产。
- 建议：Phase 0 必须有一个最小上下文裁剪策略，不能等 RAG。最简方案：按选中字幕时间戳取前后 N 分钟逐字稿片段 + 课件全文（或课件按章节标题粗筛）。这是时间窗截取，工程量很小。

### F5. 字幕格式容错策略缺失，"可换素材"对用户过于苛刻
- R-04 应对方案是"仅对标准VTT开启"——这是产品化阶段策略。Phase 0 用户自备字幕来源复杂（srt、ass、B站CC、自动生成带样式标签的 webvtt），一刀切"仅标准 VTT"等于大部分用户用不了。
- F3 说"可换素材"是核心诉求，F5 说只支持标准 VTT——叠加后"可换素材"接近不可用。
- 建议：明确 Phase 0 支持的格式清单（至少 vtt + srt），非标格式的检测方式，字幕选中失败的降级方案。

## 二、重要遗漏（要补但可与开发并行）

- I1. 多轮追问的上下文管理未定义（全量重传 vs 历史对话 vs 摘要）
- I2. 流式输出中断与并发处理（网络抖动、用户切走、流式中再提问）
- I3. 错误处理与降级文案（key 失效、限流、超时、余额不足）
- I4. 管理台鉴权与访问控制（Phase 0 无用户系统但管理台不能裸奔，最小方案：localhost 绑定 + 单密码）
- I5. 部署形态未定（本地 Node / Docker / 云函数，B 站评审时谁起服务）
- I6. 课件格式约束过窄（真实课件 80% 是 PPT/PDF，只支持 Markdown 等于让用户做数据清洗）

---

## 三、轻量方案合理性拷问

1. "用户自备 VTT 字幕"假设过于乐观——用户能拿到的大部分是 srt/ass/B站CC。至少要内置 srt→vtt 转换或同时支持 srt。
2. "Markdown 课件"假设脱离实际——真实课件 80% 是 PPT/PDF。
3. "大模型按 prompt 约束只基于课程内容回答"是幻觉——模型对 prompt 约束服从度有限，Phase 0 没有 RAG/引用标注/超范围检测。
4. "原型不引入 RAG 全量传入上下文"在 Phase 0 失效——对 1 小时以上课程直接失效。最小时间窗截取工程量很小。
5. "Phase 0 没用户系统"与"管理台不裸奔"叠加，必然推出"必须有最小鉴权"。
6. "B 站评审用"与"自用独立产品"两个目标优先级冲突时谁让步未定。
7. "独立网页 Demo 不侵入 B 站"与"管理台+后端+可换素材"叠加后，交付物已经不是"一个 H5 网页"了。

## 四、推进指令

### 致命项清单（优先级排序）

| 优先级 | 项 | 理由 |
|---|---|---|
| P0-1 | 范围错位重评（重做风险登记册） | 源头问题，不解决后面所有"原型可接受"都站不住 |
| P0-2 | 管理台最小设计（存储/鉴权/key保护/入口） | 从 0 开始的设计，决定后端形态 |
| P0-3 | 可换素材承载方式（三选一）+ 格式约束清单 | 决定后端职责和前端能否实现 |
| P0-4 | Token 超限处理策略（时间窗截取最小方案） | 核心链路能否跑通 |
| P0-5 | 字幕格式容错（vtt+srt 至少双支持 + 降级） | 决定"可换素材"是否真的可用 |

### 建议下一步

**先补 P0-1、P0-2、P0-3 再审一次，然后带 P0-4、P0-5 进 PRD 让 PRD 细化。**

- P0-1/2/3 决定整体架构（有没有后端、后端多大、前端怎么读素材、key 放哪）。这三项不定，PRD 没法写。
- P0-4/5 是"在已定架构内怎么实现"的问题，PRD 阶段细化合适，但要在 PRD 里显式列为待决项。
- 不要带 P0-1/2/3 进开发。任何一项后补都会导致前后端返工。

强烈建议：把"Phase 0 范围"和"提议书 Phase 0 范围"的差异写成显式变更说明，附在提议书后作为 V1.3。
